# Memory and Knowledge

Carter has a two-tier system for accumulating and reusing experience across conversations: **memory** (fast, unstructured notes) and **knowledge** (curated, structured entries). Memory is the input funnel; knowledge is the long-term store.

## Architecture Overview

```
Conversation → /memories/ (fast capture) → carter-distill → ~/.copilot/knowledge/ (curated)
                   ▲                                                ▲
                   │                                                │
            carter-mistakes                                 read before acting
            (structured recording)                        (global instruction)
```

There are two distinct storage locations, three skills involved, and one global instruction that ties it all together.

## Tier 1: Memory (`/memories/`)

Memory is a **platform-provided tool** — it is not part of Carter's codebase. VS Code Copilot and compatible clients expose a `memory` tool with three scopes:

| Scope | Path | Persistence | Purpose |
|-------|------|-------------|---------|
| User | `/memories/` | Across all workspaces and conversations | Preferences, general insights, recurring patterns |
| Session | `/memories/session/` | Current conversation only | Task-specific context, in-progress working notes |
| Repository | `/memories/repo/` | Current workspace | Codebase conventions, project-specific facts |

### How memory works

- **User memory** is loaded into the agent's context automatically (first 200 lines). This makes it the most immediately useful scope — anything written here is available on every future turn without explicit retrieval.
- **Session memory** files are listed in context but not loaded automatically. The agent must read them explicitly. They are cleared when the conversation ends.
- **Repository memory** is stored locally in the workspace and scoped to that repository.

### What gets written to memory

Carter writes to `/memories/` in two ways:

1. **Automatically by carter-mistakes** — When a mistake or failure is identified during work, the `carter-mistakes` skill writes a structured note to `/memories/` with fields for context, root cause, fix, and lesson.

2. **Ad-hoc by any agent** — Any Carter agent can write to `/memories/` at any time using the memory tool. Common triggers: the user says "remember this," a debugging session uncovers a useful pattern, or an agent encounters something worth preserving.

### Memory is ephemeral by design

Memory notes are quick captures — they may be incomplete, context-dependent, or duplicative. They are not meant to be the final destination. The expectation is that valuable notes get promoted to knowledge, and the rest get cleaned up.

## Tier 2: Knowledge (`~/.copilot/knowledge/`)

Knowledge is Carter's **curated, long-term store**. It lives on disk at `~/.copilot/knowledge/` and consists of six topic-specific Markdown files:

| File | Content Type | Key Fields |
|------|-------------|------------|
| `decisions.md` | Architecture Decision Records | Context, Decision, Rationale, Alternatives, Tags |
| `mistakes.md` | Failures and corrective lessons | Context, Mistake, Fix, Lesson, Tags |
| `patterns.md` | Recurring design patterns | Context, Pattern, When to use, Example, Tags |
| `debugging.md` | Debugging techniques and fixes | Context, Symptom, Root cause, Fix, Tags |
| `infrastructure.md` | Cloud/infra configurations | Context, Configuration, Outcome, Tags |
| `project-history.md` | Project milestones and outcomes | Project, Milestone, Outcome, Tags |

### Entry format

Every entry follows a consistent Markdown structure:

```markdown
## YYYY-MM-DD | Title
- **Context:** Where this happened (repo, file, project)
- **[Topic-specific fields]:** ...
- **Tags:** comma-separated keywords
```

The date prefix enables chronological reading. Tags enable searchability across files.

### How knowledge files are installed

The installer (`install.py`) copies template files from the repository's `knowledge/` directory to `~/.copilot/knowledge/`. Each template contains only the title, description, and a commented-out format guide — no entries.

**Critical behavior**: the installer uses a no-overwrite policy. If a knowledge file already exists at the destination, it is skipped entirely. This prevents the installer from wiping out user-curated entries on re-install or update. This is different from agent and skill files, which are overwritten on update.

### How knowledge is read

Two global rules files instruct every agent to use the knowledge base:

- **`copilot-instructions.md`** (VS Code + Copilot CLI): "Consult `~/.copilot/knowledge/` before proposing solutions to check for past decisions and lessons."
- **`AGENTS.md`** (OpenCode): Contains the same memory rules, generated by the installer.

This means any Carter agent — before designing a solution, choosing an approach, or making a recommendation — should check whether the knowledge base already contains relevant decisions, past mistakes, or proven patterns. This is the mechanism that closes the learning loop: knowledge captured in one conversation influences decisions in future conversations.

## Skills That Drive the System

### carter-mistakes

**Owner**: `@carter-learner`

**Purpose**: Capture mistakes and failures as they happen, in a structured format.

**Trigger**: When a mistake or failure is identified during a conversation. The user might say "record this mistake" or the agent might proactively identify a failure worth capturing.

**Workflow**:
1. Identify the mistake — what specifically went wrong
2. Capture context — repository, file, what was being attempted
3. Root cause — why it happened (not surface symptoms)
4. Fix — what resolved it
5. Lesson — what to do differently next time (the core takeaway)
6. Write a structured note to `/memories/`
7. If enough notes have accumulated, suggest running `carter-distill`

**Output**: A Markdown note in `/memories/` with the full structure (date, context, what went wrong, root cause, fix, lesson, tags).

**Guidelines**: No blame (focus on systemic cause), be specific (not "Terraform failed" but "Terraform failed because the S3 bucket policy referenced a deleted IAM role"), check for duplicates against existing `~/.copilot/knowledge/mistakes.md`, and use meaningful tags.

### carter-distill

**Owner**: `@carter-maestro`

**Purpose**: Promote raw memory notes into curated knowledge entries.

**Trigger**: On-demand only — the user asks for it. Never auto-runs. Typical invocation: `@carter-maestro distill` or `distill my notes`.

**Workflow**:
1. **Read** — Scan all notes in `/memories/` (user and repo scope)
2. **Classify** — Map each note to one of the six knowledge topics
3. **Deduplicate** — Check existing entries in the target knowledge file; skip if a substantially similar entry already exists
4. **Format** — Structure each entry using the standard Markdown format
5. **Append** — Add new entries to the appropriate `~/.copilot/knowledge/` file
6. **Report** — Show what was promoted: count per topic, skipped duplicates
7. **Suggest cleanup** — Recommend which `/memories/` notes can be deleted

**Guidelines**: Only run when asked, preserve the user's original meaning, ask when classification is unclear, and create entries in multiple files if a note spans topics.

### carter-explain and carter-research

These are `@carter-learner` skills that read from the knowledge base but don't write to it. They may reference past decisions or patterns when explaining topics, leveraging the knowledge base as a source alongside official documentation.

## Agent Roles

### carter-learner

The knowledge specialist. Has `carter-mistakes`, `carter-explain`, and `carter-research` as skills. Primary responsibilities:
- Recording mistakes and extracting learnable patterns
- Breaking down complex topics with cited sources
- Researching official documentation

Maestro routes requests to Learner when the user says things like: "explain," "learn," "document," "research," "why," "how does," "teach."

### carter-maestro

The orchestrator. Has `carter-distill` as a skill (alongside `carter-triage`). Maestro is the entry point for the distill workflow — the user asks Maestro to distill, and Maestro runs the skill directly.

### All agents

Every agent follows the global instruction to consult `~/.copilot/knowledge/` before proposing solutions. This rule lives in two global rules files: `copilot-instructions.md` (VS Code + Copilot CLI) and `AGENTS.md` (OpenCode). Both are generated by the installer.

## Information Flow

The complete lifecycle of a piece of knowledge:

```
1. Failure occurs during work
         │
         ▼
2. carter-mistakes records it to /memories/
   (structured: context, root cause, fix, lesson)
         │
         ▼
3. Note sits in /memories/ (fast capture)
   May accumulate alongside other notes
         │
         ▼
4. User runs: @carter-maestro distill
         │
         ▼
5. carter-distill reads /memories/
   Classifies → Deduplicates → Formats → Appends
         │
         ▼
6. Entry lands in ~/.copilot/knowledge/mistakes.md
   (or decisions.md, patterns.md, etc.)
         │
         ▼
7. Future conversation: any agent consults knowledge/
   before proposing a solution → avoids repeating mistake
```

Not all knowledge follows this exact path. Some entries bypass the `/memories/` step — a user might ask Maestro to distill something directly from a conversation, or manually edit the knowledge files. The system is flexible.

## Cross-Surface Behavior

The memory and knowledge system works across all three surfaces Carter supports:

| Surface | Memory tool | Knowledge files | Distill |
|---------|-----------|----------------|---------|
| VS Code (Copilot Chat) | Built-in `memory` tool | Read via file tools | Works via skill |
| Copilot CLI | Platform memory tool | Read via file tools | Works via skill |
| OpenCode | Platform memory tool | Read via file tools | Works via skill |

The global instruction ("consult `~/.copilot/knowledge/`") is in `copilot-instructions.md` (loaded by VS Code and Copilot CLI) and in the generated `AGENTS.md` (loaded by OpenCode). Both files are maintained by the installer.

## Installation

The installer handles knowledge setup:

```bash
uv run install.py                    # Installs templates to ~/.copilot/knowledge/
uv run install.py --target opencode  # Same — knowledge is copilot-only
```

Knowledge files are only installed to the copilot base directory (`~/.copilot/knowledge/`), not to OpenCode's directory. All surfaces read from the same location.

### What the installer does

1. Copies six template files from `knowledge/` to `~/.copilot/knowledge/`
2. **Skips existing files** — never overwrites user content
3. Records installed files in the manifest (`.carter-manifest.json`)

### What the installer does NOT do

- Does not initialize a Git repository in the knowledge directory (planned for v2)
- Does not sync knowledge across machines (planned for v2)
- Does not create any `/memories/` files (those are platform-managed)

## Future: Git-Backed Knowledge Sync (v2)

The v2 plan includes syncing knowledge across machines via a Git repository:

- **New installer flag**: `--knowledge-repo <url>` — clones a repo to `~/.copilot/knowledge/` instead of copying templates
- **Auto-commit**: `carter-distill` would auto-commit after appending entries, with structured commit messages
- **New skill**: `carter-knowledge-sync` for pulling/pushing knowledge across machines
- **Push gating**: Push only on explicit request (`@carter-maestro distill --push`)

This is not yet implemented. Currently, knowledge files are local to the machine.
