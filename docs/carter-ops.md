# Carter-Ops

Carter-ops handles **write operations** (git, GitHub, Jira) with bot attribution, an approval gate, and audit logging.

## The Problem It Solves

AI assistants can run terminal commands. That's powerful but dangerous — an unchecked `git push --force` or accidental Jira spam is hard to undo. Carter-ops enforces a **plan → approve → execute** workflow for every write operation.

It also solves the **attribution problem**: when an AI helps write a commit, who authored it? You do — commits keep your git identity and are signed with your key, and the AI's help is credited with a `Co-authored-by: carter-bot <…>` trailer (the bot identity from `~/.carter/config.toml`). GitHub shows both.

## How It Works

```
You: "ops: create branch, commit changes, push"
      │
      ▼
Agent loads the carter-ops skill
      │
      ├─ 1. ASSESS  → git status, git diff (reads — no approval needed)
      ├─ 2. PLAN    → shows exact commands (co-author trailer on commits)
      ├─ 3. APPROVE → waits for your "yes" before doing anything
      ├─ 4. EXECUTE → runs the commands in the terminal
      ├─ 5. AUDIT   → carter ops audit --operation ... --result success
      └─ 6. REPORT  → tells you what happened (SHA, branch, URL)
```

**Key principle:** the model runs git / `gh` / `curl` commands directly. The `carter ops` subcommand is only a small utility around that: it prints config values, records audit entries, and records policy overrides. It does not execute operations itself.

The protocol lives in a single skill, `skills/carter-ops/SKILL.md`. It is triggered by the `ops:` prefix: every globally installed agent (`agents/*.md`), the global `instructions/copilot-instructions.md`, and OpenCode's global `AGENTS.md` carry the one-liner *"When the user's request starts with `ops:`, load the `carter-ops` skill and follow its instructions exactly."*

## Setup

`carter install` generates `~/.carter/config.toml` (only if it doesn't exist yet) and installs the skill with your attribution values substituted into it:

```bash
carter install                       # bot name: carter-bot
carter install --bot-name "acme-bot" # author: acme-bot <acme-bot@users.noreply.github.com>
```

### Config file

Non-secret settings live in `~/.carter/config.toml`:

```toml
[attribution]
# Co-author identity: credited via a `Co-authored-by:` trailer on commits
# (you stay the author) and in GitHub/Jira footers.
name = "carter-bot"                              # set via --bot-name at install time
email = "carter-bot@users.noreply.github.com"    # derived from name
footer = "This comment was generated by carter-bot."

[git]
signing_key = "~/.ssh/id_ed25519"

[jira]
url = ""
email = ""
# token comes from JIRA_TOKEN or ATLASSIAN_API_TOKEN env var — never in config file
```

The signing key is auto-detected from `git config user.signingkey` at install time. If it is still empty at runtime, `carter ops config --emit` falls back to `~/.ssh/id_ed25519`, then `~/.ssh/id_rsa`.

### Environment variables

Secrets always come from the environment:

| Variable | Used for |
|----------|----------|
| `GITHUB_TOKEN` | `gh` writes; reported as `has_github_token` |
| `JIRA_TOKEN` / `ATLASSIAN_API_TOKEN` | Jira REST calls; reported as `has_jira_token` |
| `ATLASSIAN_URL`, `ATLASSIAN_EMAIL` | Jira REST calls; override `[jira]` in `config.toml` |

## `carter ops` reference

All output is JSON on stdout; errors go to stderr. Exit code `0` = success, `1` = usage/validation error.

| Command | Purpose |
|---------|---------|
| `carter ops config --emit` | Print attribution/config values (bot name, email, signing key, footer, Jira URL/email, whether tokens are set) |
| `carter ops audit --operation <name> --result <success\|failure> [--params '<json>'] [--identifiers '<json>']` | Append an audit entry after the model ran the commands |
| `carter ops policy-override --category <cat> --action <action> --tier <tier> [--reason <text>]` | Record a single-action strictness-policy override |

### Audit log

Entries are appended to `~/.carter/audit.log` as JSONL:

```json
{"timestamp": "2026-10-24T17:05:58+00:00", "operation": "git-flow", "phase": "execute",
 "result": "success", "params": {"branch": "feature/x"}, "identifiers": {"commit_sha": "abc1234"}}
```

Logging is best-effort: if the write fails, nothing else is affected. Git/GitHub/Jira history remains the authoritative record.

### Policy override (escape hatch)

When the [strictness policy](strictness-policy.md) gates an action, record a deliberate single-action override. **Override ≠ authorization**: the ledger *records* that you overrode a gate; it cannot lift a platform `deny`. There is no blanket or session-wide override.

```bash
carter ops policy-override \
  --category remote-write \
  --action "git push origin main" \
  --tier native-ask \
  --reason "hotfix release"
```

| Param | Required | Description |
|-------|----------|-------------|
| `--category` | Yes | Risk category being overridden: `read`, `local-write`, `remote-write`, `dangerous` |
| `--action` | Yes | The exact action overridden (max 500 chars) |
| `--tier` | Yes | `native-deny` (relaxed emitted config) · `native-ask` (confirmed a prompt) · `prose-backstop` (proceeded on trust) |
| `--reason` | No | Free-text justification (recorded, never a secret; max 500 chars) |

Every entry carries `"authorized": false` and lands in `~/.carter/audit.log`.

## Attribution

- **Git** — you are the commit author (your `git config user.name/email`) and commits are signed with your key (`-S`). The bot is credited only through a `Co-authored-by: <name> <email>` trailer; Carter never passes `--author`.
- **GitHub** — issues, PRs and comments are posted under your account (`gh`); a Markdown footer `_This was generated by <name>._` is appended.
- **Jira** — comments are posted under your account (API limitation); the footer `_This comment was generated by <name>._` is appended.

## Read/write boundary

| Operation type | How |
|---|---|
| Git writes (commit, push, branch) | Model runs git directly: `-S` + `Co-authored-by:` trailer, English message |
| Git reads (log, status, diff, blame) | Direct git commands (no `ops:` needed) |
| Jira writes (create, comment, transition) | Model runs `curl` against REST API v2 |
| Jira reads (search, view ticket) | `carter-atlassian` MCP server |
| GitHub reads (PRs, issues, Actions) | `carter-github` MCP server or `gh` |
| GitHub writes (issues, PRs, comments) | Model runs `gh` with the footer |

## Why direct execution

Earlier versions had the model call `carter ops <operation> --dry-run|--execute` wrappers. Agents consistently "mimed" that protocol, inventing JSON output or running raw commands anyway: **instructions cannot force tool invocation.** The current design works with model behavior. The model shows its own plan, you approve it, it runs the commands it already knows (with the co-author identity baked into the skill at install time), and `carter ops audit` records the result afterwards.
