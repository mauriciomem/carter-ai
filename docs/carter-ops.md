# Carter-Ops

Carter-ops is a deterministic CLI executor for write operations. It enforces a clear boundary: **MCP servers handle reads**, **carter-ops handles writes**. Every write operation goes through a two-phase approval flow — dry-run first, execute after approval.

## Why

LLMs interpret natural-language instructions inconsistently across models. A shared instructions file telling agents "always confirm before committing" works sometimes, but breaks across Claude, GPT-4, Gemini, and model updates.

Carter-ops moves the deterministic zone from instructions to code. The LLM prepares the parameters; carter-ops validates and executes them identically every time.

## Architecture

```
User request
  │
  └─→ Agent (carter-devops / carter-pm)
        │
        ├─ READ: MCP servers, direct commands (git log, JQL, etc.)
        │
        └─ WRITE: carter-ops via terminal
              │
              ├─ --dry-run  → JSON plan shown to user
              ├─ user approves
              └─ --execute  → deterministic execution → JSON result
```

Carter-ops is a **dumb executor**. It never decides what to do — only does what it's told, safely. Content generation (commit messages, ticket descriptions) is the skill's domain.

## Getting Started

### Prerequisites

- Python 3.11+
- [uv](https://docs.astral.sh/uv/)
- Git (for git operations)
- Jira API access (for Jira operations — optional)

### Installation

Carter-ops is installed automatically by the Carter installer:

```bash
uv run install.py
```

This does three things:

1. Copies `ops/` to `~/.carter/ops/`
2. Generates `~/.carter/config.toml` with auto-detected settings
3. Creates `~/.local/bin/carter-ops` wrapper script

### Verify Installation

```bash
carter-ops --list
```

Expected output:

```json
{
  "operations": [
    "git-branch",
    "git-commit",
    "git-flow",
    "git-push",
    "jira-comment",
    "jira-create",
    "jira-update"
  ]
}
```

### PATH Setup

If `carter-ops` is not found, add `~/.local/bin` to your PATH:

```bash
# Add to ~/.zshrc (macOS) or ~/.bashrc (Linux)
export PATH="$HOME/.local/bin:$PATH"
```

## Configuration

### Config File

Non-secret settings live in `~/.carter/config.toml`:

```toml
[attribution]
name = "carter-bot"
email = "carter-bot@users.noreply.github.com"
footer = "This comment was generated by carter-bot."

[git]
signing_key = "~/.ssh/id_ed25519"

[jira]
url = "https://your-domain.atlassian.net"
email = "you@company.com"
# token comes from env var — never in config file
```

The installer generates this file with sensible defaults. The git signing key is auto-detected from `git config user.signingkey` if set, otherwise it checks `~/.ssh/id_ed25519` and `~/.ssh/id_rsa`.

### Environment Variables (Secrets)

Jira credentials are always loaded from environment variables:

```bash
export JIRA_TOKEN="your_api_token"
# or
export ATLASSIAN_API_TOKEN="your_api_token"
export ATLASSIAN_EMAIL="you@company.com"
export ATLASSIAN_URL="https://your-domain.atlassian.net"
```

Environment variables override config file values for `jira_url` and `jira_email`.

## Usage

### Two-Phase Workflow

Every operation follows the same pattern:

```bash
# Phase 1: Dry-run — see the plan
carter-ops <operation> [params] --dry-run

# Phase 2: Execute — do it
carter-ops <operation> [params] --execute
```

The same params are replayed in both phases. No state is stored between phases — carter-ops is stateless.

### Example: Create a Branch and Commit

```bash
# See the plan
carter-ops git-flow \
  --branch feature/PROJ-123-add-auth \
  --message "feat: add authentication module" \
  --files src/auth.py \
  --from main \
  --dry-run
```

Output:

```json
{
  "phase": "dry-run",
  "operation": "git-flow",
  "steps": [
    "git checkout main",
    "git pull origin main",
    "git checkout -b feature/PROJ-123-add-auth",
    "git add src/auth.py",
    "git commit --author='carter-bot <carter-bot@users.noreply.github.com>' -S -m 'feat: add authentication module'",
    "git push origin feature/PROJ-123-add-auth"
  ],
  "attribution": "Author: carter-bot, Signed-by: user (~/.ssh/id_ed25519)",
  "side_effects": [
    "New branch 'feature/PROJ-123-add-auth' from 'main'",
    "1 new commit as carter-bot",
    "Branch pushed to origin"
  ]
}
```

```bash
# Execute after reviewing
carter-ops git-flow \
  --branch feature/PROJ-123-add-auth \
  --message "feat: add authentication module" \
  --files src/auth.py \
  --from main \
  --execute
```

## Operations Reference

### Git Operations

#### `git-branch`

Create a new branch from a base branch.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--name` | Yes | — | Branch name |
| `--from` | No | `main` | Base branch |

```bash
carter-ops git-branch --name feature/PROJ-123 --from main --dry-run
```

#### `git-commit`

Stage files and commit as carter-bot.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--message` | Yes | — | Commit message |
| `--files` | No | `.` | Files to stage (comma-separated or repeated) |

```bash
carter-ops git-commit --message "feat: add auth" --files src/auth.py,src/config.py --dry-run
```

Commits are signed with the configured SSH key (`-S`) and authored by carter-bot (`--author`). GitHub shows: *Signed by mmitolo, authored by carter-bot*.

#### `git-push`

Push a branch to origin.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--branch` | No | current branch | Branch to push |

```bash
carter-ops git-push --branch feature/PROJ-123 --dry-run
```

#### `git-flow` (Composite)

Branch → add → commit → push in one operation.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--branch` | Yes | — | New branch name |
| `--message` | Yes | — | Commit message |
| `--files` | No | `.` | Files to stage |
| `--from` | No | `main` | Base branch |

```bash
carter-ops git-flow \
  --branch feature/PROJ-123 \
  --message "feat: add auth" \
  --files src/auth.py \
  --dry-run
```

### Jira Operations

Jira operations require `JIRA_TOKEN` (or `ATLASSIAN_API_TOKEN`), `ATLASSIAN_EMAIL`, and `ATLASSIAN_URL` to be set.

#### `jira-comment`

Add a comment to a Jira ticket. The carter-bot footer is automatically appended.

| Param | Required | Description |
|-------|----------|-------------|
| `--ticket` | Yes | Ticket key (e.g., `PROJ-123`) |
| `--body` | Yes | Comment text |

```bash
carter-ops jira-comment \
  --ticket PROJ-123 \
  --body "Completed the auth module implementation" \
  --dry-run
```

#### `jira-create`

Create a new Jira ticket.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--project` | Yes | — | Project key |
| `--type` | Yes | — | Issue type (Story, Bug, Task, Epic) |
| `--summary` | Yes | — | Ticket title |
| `--description` | No | — | Full description |
| `--priority` | No | `Medium` | Priority level |
| `--labels` | No | — | Comma-separated labels |

```bash
carter-ops jira-create \
  --project PROJ \
  --type Story \
  --summary "Add authentication module" \
  --description "Implement OAuth2 flow for the API gateway" \
  --priority High \
  --labels auth,api \
  --dry-run
```

#### `jira-update` (Composite)

Add a comment and/or transition a ticket's status.

| Param | Required | Description |
|-------|----------|-------------|
| `--ticket` | Yes | Ticket key |
| `--comment` | No* | Comment text |
| `--transition` | No* | Target status name (e.g., "In Progress", "Done") |

\* At least one of `--comment` or `--transition` is required.

```bash
carter-ops jira-update \
  --ticket PROJ-123 \
  --comment "Implementation complete, moving to review" \
  --transition "In Review" \
  --dry-run
```

## Output Contract

### JSON to stdout

All output is structured JSON to stdout. Human-readable errors go to stderr.

### Exit Codes

| Code | Meaning |
|------|---------|
| `0` | Success (dry-run plan or execution completed) |
| `1` | Validation error (missing params, bad ticket key, branch already exists) |
| `2` | Execution error (git push rejected, Jira API 403, network failure) |
| `3` | Configuration error (missing env vars, signing key not found) |

### Output Formats

**Dry-run:**

```json
{
  "phase": "dry-run",
  "operation": "git-commit",
  "steps": ["git add src/auth.py", "git commit --author='carter-bot <...>' -S -m '...'"],
  "attribution": "Author: carter-bot, Signed-by: mmitolo",
  "side_effects": ["1 new commit on feature/PROJ-123-add-auth"]
}
```

**Execute (success):**

```json
{
  "phase": "execute",
  "operation": "git-commit",
  "success": true,
  "result": {"commit_sha": "a1b2c3d", "branch": "feature/PROJ-123", "files_committed": 1},
  "attribution": "Author: carter-bot, Signed-by: mmitolo"
}
```

**Execute (error):**

```json
{
  "phase": "execute",
  "operation": "git-push",
  "success": false,
  "error": {
    "code": "PUSH_REJECTED",
    "message": "Remote has changes not present locally. Pull first.",
    "suggestion": "Run: git pull origin feature/PROJ-123 --rebase"
  }
}
```

The `suggestion` field tells the LLM what to do next on failure — keeping recovery deterministic.

## Attribution

### Git

Commits use `--author="carter-bot <carter-bot@users.noreply.github.com>"` and are signed with the user's SSH key (`-S`). GitHub shows the commit as *authored by carter-bot, signed by you* — honest, verifiable attribution.

### Jira

Comments are posted under your Jira account (API limitation). A footer is appended to every comment and description:

> _This comment was generated by carter-bot._

Both the author name, email, and footer text are configurable in `~/.carter/config.toml`.

## Audit Log

Every operation (dry-run and execute) is appended to `~/.carter/audit.log` as JSONL. Each entry includes:

- `timestamp` (ISO 8601)
- `operation` name
- `phase` (dry-run or execute)
- `params` (minus secrets and large text fields)
- `result` (success/failure + key identifiers)

The audit log is append-only and best-effort — if the write fails, the operation still proceeds.

## Extending Carter-Ops

### Adding a New Operation

1. Create a new file in `ops/operations/` (e.g., `git_pr.py`)
2. Implement the `Operation` base class with `dry_run()` and `execute()`
3. Decorate with `@register`

```python
from operations import Operation, Plan, Result, register
from config import Config

@register
class GitPR(Operation):
    name = "git-pr"

    def validate(self, params):
        errors = []
        if not params.get("title"):
            errors.append("--title is required")
        return errors

    def dry_run(self, params, cfg):
        return Plan(
            operation=self.name,
            steps=[f"gh pr create --title '{params['title']}' --draft"],
            attribution=attribution_summary(cfg, "git"),
            side_effects=["New draft PR created"],
        )

    def execute(self, params, cfg):
        # ... subprocess.run(["gh", "pr", "create", ...])
        return Result(...)
```

The operation is auto-discovered at startup — no registration code changes needed.

### Adding Tests

Add a test file in `tests/ops/` following the existing pattern:

```python
class TestGitPRDryRun:
    def test_dry_run(self):
        from operations import discover_operations, get_operation
        from config import Config

        discover_operations()
        op = get_operation("git-pr")
        plan = op.dry_run({"title": "Add auth"}, Config())
        assert plan.operation == "git-pr"
```

## How Agents Enforce Carter-Ops

The carter-ops protocol is enforced at three layers to ensure it works across all surfaces (VS Code, Copilot CLI, OpenCode). Each layer uses **explicit terminal invocation language** — instructions say "run in the terminal" not "use carter-ops" — because LLMs interpret "use" as "apply the concept" rather than "invoke the CLI."

### Anti-Pattern: Protocol Mime

In testing, agents would **understand** the carter-ops protocol, recognize `ops:` triggers, format their own JSON plan, ask for approval — then run raw `git commit` and `git push`. The model **mimed** the protocol without invoking the tool. This happens because:

1. "Use carter-ops" is ambiguous — the model applies the concept by fabricating output
2. `<guidelines>` sections with raw git write command examples provide a competing template
3. Carter-ops instructions at the bottom of files lose primacy to earlier content

All three layers now address this with: imperative terminal language, explicit fabrication prohibition, write command examples removed from guidelines, and carter-ops sections positioned first.

### Layer 1: Global Instructions

The file `instructions/copilot-instructions.md` starts with a "CRITICAL: Write Operations" section — positioned **first**, before all other instructions. It includes:
- Explicit forbidden commands list
- Required workflow with "**in the terminal**" at every step
- "What NOT to do" section with wrong (fabricated output, raw git) and right (actual carter-ops terminal output) examples

This file is loaded by **every agent on every surface** — it's the universal safety net.

### Layer 2: Agent Definitions

Each agent that handles write operations (`carter-maestro`, `carter-devops`, `carter-pm`) has a "CRITICAL: Write Operations" section **positioned immediately after `</role>`** — before routing rules, skills, or MCP config. This matters because:

- In **Copilot CLI**, there's no subagent delegation — the selected agent (often Maestro) executes directly. The agent must know the protocol itself.
- In **VS Code**, an agent might handle a task without loading a skill if the request seems simple.
- **Primacy**: The constraint appears before the agent starts planning its approach.

Maestro's section includes a complete step-by-step example showing the exact terminal commands for a git-flow operation.

### Layer 3: Skill `<deterministic-operations>` Blocks

Skills that involve write operations include a `<deterministic-operations>` block **positioned before `<guidelines>`** in their SKILL.md. This ensures the agent reads the constraint before seeing any command examples. Write command examples (git commit, git push, git add) have been **removed from `<guidelines>`** — only read command examples remain.

Currently applied to:
- **carter-pipeline** — git write operations
- **carter-atlassian** — Jira write operations

### Why Three Layers

No single layer is guaranteed to be loaded on every surface. Copilot CLI may not load user-level instructions (Layer 1). An agent might skip a skill for "simple" requests (Layer 3). The agent file (Layer 2) is the most reliably loaded, but all three reinforce the same constraint with the same language.

## Read/Write Boundary

| Operation type | Tool |
|---|---|
| Git writes (commit, push, branch) | `carter-ops` via terminal |
| Git reads (log, status, diff, blame) | Direct git commands |
| Jira writes (create, comment, transition) | `carter-ops` via terminal |
| Jira reads (search, view ticket) | `carter-atlassian` MCP server |
| GitHub reads (PRs, issues, Actions) | `carter-github` MCP server |
| GitHub writes (create PR, merge) | Future `carter-ops` operation |

## Design Decisions

Full design rationale is in [docs/interactions/conversation-log-carter-ops.md](interactions/conversation-log-carter-ops.md). Key decisions:

1. **CLI over MCP server** — LLMs can reliably call CLI tools via terminal across all surfaces
2. **Stateless two-phase** — No execution IDs to track; replay params for execute
3. **Python** — Matches the existing toolchain; `uv run` for dependency isolation
4. **Plugin pattern** — New operation = new file, no framework changes
5. **JSON output** — Structured for LLM consumption; stderr for humans
6. **Code over instructions** — Deterministic behavior regardless of LLM model
7. **Three-layer enforcement with explicit terminal invocation** — Global instructions + agent definitions + skill blocks, all using imperative "run in the terminal" language. Previous iterations used advisory language ("use carter-ops") which models interpreted as "implement the protocol yourself." v3 adds explicit negative examples ("do NOT fabricate output"), removes competing write command examples from skill guidelines, and positions the constraint first in every file.
