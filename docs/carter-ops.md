# Carter-Ops

Carter-ops handles **write operations** (git, GitHub, Jira) with bot attribution, approval gates, and audit logging.

## The Problem It Solves

AI assistants can run terminal commands. That's powerful but dangerous — an unchecked `git push --force` or accidental Jira spam is hard to undo. Carter-ops solves this by enforcing a **plan → approve → execute** workflow for every write operation.

It also solves the **attribution problem**: when an AI makes a commit, who authored it? Carter-ops attributes commits to a bot identity (e.g., `mauri-droid`) while signing them with your SSH key. This makes it clear which commits are AI-assisted while keeping them cryptographically tied to you.

## How It Works (Mental Model)

```
You: "ops: create branch, commit changes, push"
      │
      ▼
Agent loads carter-ops skill
      │
      ├─ 1. ASSESS  → git status, git diff (reads — no approval needed)
      ├─ 2. PLAN    → shows exact commands with attribution flags
      ├─ 3. APPROVE → waits for your "yes" before doing anything
      ├─ 4. EXECUTE → runs commands in terminal
      ├─ 5. AUDIT   → carter ops audit --operation ... --result success
      └─ 6. REPORT  → tells you what happened (SHA, branch, URL)
```

**Key principle:** The model runs commands directly in the terminal (not through a CLI wrapper). Carter-ops provides the supporting utilities: config values, attribution flags, and audit logging.

## Getting Started

### Prerequisites

- Python 3.11+
- [uv](https://docs.astral.sh/uv/)
- Git (for git operations)
- Jira API access (for Jira operations — optional)
- GitHub API access (for GitHub operations — optional)

### Installation

Carter-ops ships as the `ops` subcommand of the unified `carter` CLI. Install the CLI once with `uv`:

```bash
uv tool install git+https://github.com/mauriciomem/carter-ai.git
```

Then generate the global config (auto-detected settings and bot name):

```bash
carter install
```

This generates `~/.carter/config.toml` with auto-detected settings and bot name.

To use a custom bot name:

```bash
carter install --bot-name "acme-bot"
```

This sets the git commit author to `acme-bot <acme-bot@users.noreply.github.com>` and updates the Jira footer accordingly.

### Verify Installation

```bash
carter ops --list
```

Expected output:

```json
{
  "operations": [
    "gh-issue",
    "gh-issue-comment",
    "gh-pr",
    "gh-pr-comment",
    "git-branch",
    "git-commit",
    "git-flow",
    "git-push",
    "jira-comment",
    "jira-create",
    "jira-update"
  ]
}
```

### PATH Setup

If `carter` is not found, add `~/.local/bin` to your PATH:

```bash
# Add to ~/.zshrc (macOS) or ~/.bashrc (Linux)
export PATH="$HOME/.local/bin:$PATH"
```

## Configuration

### Config File

Non-secret settings live in `~/.carter/config.toml`:

```toml
[attribution]
name = "carter-bot"                              # set via --bot-name at install time
email = "carter-bot@users.noreply.github.com"    # derived from name
footer = "This comment was generated by carter-bot."

[git]
signing_key = "~/.ssh/id_ed25519"

[jira]
url = "https://your-domain.atlassian.net"
email = "you@company.com"
# token comes from env var — never in config file
```

The installer generates this file with sensible defaults. The `name` field is set by `--bot-name` (default: `carter-bot`). The `email` is derived as `<name>@users.noreply.github.com`. The git signing key is auto-detected from `git config user.signingkey` if set, otherwise it checks `~/.ssh/id_ed25519` and `~/.ssh/id_rsa`.

### Environment Variables (Secrets)

Jira credentials are always loaded from environment variables:

```bash
export JIRA_TOKEN="your_api_token"
# or
export ATLASSIAN_API_TOKEN="your_api_token"
export ATLASSIAN_EMAIL="you@company.com"
export ATLASSIAN_URL="https://your-domain.atlassian.net"
```

Environment variables override config file values for `jira_url` and `jira_email`.

### GitHub Environment Variables

GitHub operations require a personal access token:

```bash
export GITHUB_TOKEN="ghp_your_token_here"
```

The token needs `repo` scope for private repos, or `public_repo` for public repos only.

## Usage

### Two-Phase Workflow

Every operation follows the same pattern:

```bash
# Phase 1: Dry-run — see the plan
carter ops <operation> [params] --dry-run

# Phase 2: Execute — do it
carter ops <operation> [params] --execute
```

The same params are replayed in both phases. No state is stored between phases — carter-ops is stateless.

### Example: Create a Branch and Commit

```bash
# See the plan
carter ops git-flow \
  --branch feature/PROJ-123-add-auth \
  --message "feat: add authentication module" \
  --files src/auth.py \
  --from main \
  --dry-run
```

Output:

```json
{
  "phase": "dry-run",
  "operation": "git-flow",
  "steps": [
    "git checkout main",
    "git pull origin main",
    "git checkout -b feature/PROJ-123-add-auth",
    "git add src/auth.py",
    "git commit --author='carter-bot <carter-bot@users.noreply.github.com>' -S -m 'feat: add authentication module'",
    "git push origin feature/PROJ-123-add-auth"
  ],
  "attribution": "Author: carter-bot, Signed-by: user (~/.ssh/id_ed25519)",
  "side_effects": [
    "New branch 'feature/PROJ-123-add-auth' from 'main'",
    "1 new commit as carter-bot",
    "Branch pushed to origin"
  ]
}
```

```bash
# Execute after reviewing
carter ops git-flow \
  --branch feature/PROJ-123-add-auth \
  --message "feat: add authentication module" \
  --files src/auth.py \
  --from main \
  --execute
```

## Operations Reference

### Git Operations

#### `git-branch`

Create a new branch from a base branch.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--name` | Yes | — | Branch name |
| `--from` | No | `main` | Base branch |

```bash
carter ops git-branch --name feature/PROJ-123 --from main --dry-run
```

#### `git-commit`

Stage files and commit as carter-bot.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--message` | Yes | — | Commit message |
| `--files` | No | `.` | Files to stage (comma-separated or repeated) |

```bash
carter ops git-commit --message "feat: add auth" --files src/auth.py,src/config.py --dry-run
```

Commits are signed with the configured SSH key (`-S`) and authored by carter-bot (`--author`). GitHub shows: *Signed by mmitolo, authored by carter-bot*.

#### `git-push`

Push a branch to origin.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--branch` | No | current branch | Branch to push |

```bash
carter ops git-push --branch feature/PROJ-123 --dry-run
```

#### `git-flow` (Composite)

Branch → add → commit → push in one operation.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--branch` | Yes | — | New branch name |
| `--message` | Yes | — | Commit message |
| `--files` | No | `.` | Files to stage |
| `--from` | No | `main` | Base branch |

```bash
carter ops git-flow \
  --branch feature/PROJ-123 \
  --message "feat: add auth" \
  --files src/auth.py \
  --dry-run
```

### Jira Operations

Jira operations require `JIRA_TOKEN` (or `ATLASSIAN_API_TOKEN`), `ATLASSIAN_EMAIL`, and `ATLASSIAN_URL` to be set.

#### `jira-comment`

Add a comment to a Jira ticket. The carter-bot footer is automatically appended.

| Param | Required | Description |
|-------|----------|-------------|
| `--ticket` | Yes | Ticket key (e.g., `PROJ-123`) |
| `--body` | Yes | Comment text |

```bash
carter ops jira-comment \
  --ticket PROJ-123 \
  --body "Completed the auth module implementation" \
  --dry-run
```

#### `jira-create`

Create a new Jira ticket.

| Param | Required | Default | Description |
|-------|----------|---------|-------------|
| `--project` | Yes | — | Project key |
| `--type` | Yes | — | Issue type (Story, Bug, Task, Epic) |
| `--summary` | Yes | — | Ticket title |
| `--description` | No | — | Full description |
| `--priority` | No | `Medium` | Priority level |
| `--labels` | No | — | Comma-separated labels |

```bash
carter ops jira-create \
  --project PROJ \
  --type Story \
  --summary "Add authentication module" \
  --description "Implement OAuth2 flow for the API gateway" \
  --priority High \
  --labels auth,api \
  --dry-run
```

#### `jira-update` (Composite)

Add a comment and/or transition a ticket's status.

| Param | Required | Description |
|-------|----------|-------------|
| `--ticket` | Yes | Ticket key |
| `--comment` | No* | Comment text |
| `--transition` | No* | Target status name (e.g., "In Progress", "Done") |

\* At least one of `--comment` or `--transition` is required.

```bash
carter ops jira-update \
  --ticket PROJ-123 \
  --comment "Implementation complete, moving to review" \
  --transition "In Review" \
  --dry-run
```

### GitHub Operations

GitHub operations require `GITHUB_TOKEN` to be set.

#### `gh-issue`

Create a new GitHub issue. The carter-bot footer is automatically appended to the body.

| Param | Required | Description |
|-------|----------|-------------|
| `--repo` | Yes | Repository in `owner/repo` format |
| `--title` | Yes | Issue title |
| `--body` | No | Issue body (Markdown) |
| `--labels` | No | Comma-separated labels |

```bash
carter ops gh-issue \
  --repo owner/repo \
  --title "Bug: auth fails on refresh" \
  --body "Token refresh returns 401" \
  --labels bug,auth \
  --dry-run
```

#### `gh-issue-comment`

Comment on an existing GitHub issue.

| Param | Required | Description |
|-------|----------|-------------|
| `--repo` | Yes | Repository in `owner/repo` format |
| `--issue` | Yes | Issue number |
| `--body` | Yes | Comment text (Markdown) |

```bash
carter ops gh-issue-comment \
  --repo owner/repo \
  --issue 42 \
  --body "Fixed in commit abc1234" \
  --dry-run
```

#### `gh-pr`

Create a new GitHub pull request.

| Param | Required | Description |
|-------|----------|-------------|
| `--repo` | Yes | Repository in `owner/repo` format |
| `--title` | Yes | PR title |
| `--head` | Yes | Source branch |
| `--base` | Yes | Target branch |
| `--body` | No | PR description (Markdown) |
| `--draft` | No | Create as draft PR |

```bash
carter ops gh-pr \
  --repo owner/repo \
  --title "feat: add auth module" \
  --head feature/auth \
  --base main \
  --body "Implements OAuth2 flow" \
  --draft \
  --dry-run
```

#### `gh-pr-comment`

Comment on an existing GitHub pull request.

| Param | Required | Description |
|-------|----------|-------------|
| `--repo` | Yes | Repository in `owner/repo` format |
| `--pr` | Yes | PR number |
| `--body` | Yes | Comment text (Markdown) |

```bash
carter ops gh-pr-comment \
  --repo owner/repo \
  --pr 99 \
  --body "LGTM, approving" \
  --dry-run
```

## Output Contract

### JSON to stdout

All output is structured JSON to stdout. Human-readable errors go to stderr.

### Exit Codes

| Code | Meaning |
|------|---------|
| `0` | Success (dry-run plan or execution completed) |
| `1` | Validation error (missing params, bad ticket key, branch already exists) |
| `2` | Execution error (git push rejected, Jira API 403, network failure) |
| `3` | Configuration error (missing env vars, signing key not found) |

### Output Formats

**Dry-run:**

```json
{
  "phase": "dry-run",
  "operation": "git-commit",
  "steps": ["git add src/auth.py", "git commit --author='carter-bot <...>' -S -m '...'"],
  "attribution": "Author: carter-bot, Signed-by: mmitolo",
  "side_effects": ["1 new commit on feature/PROJ-123-add-auth"]
}
```

**Execute (success):**

```json
{
  "phase": "execute",
  "operation": "git-commit",
  "success": true,
  "result": {"commit_sha": "a1b2c3d", "branch": "feature/PROJ-123", "files_committed": 1},
  "attribution": "Author: carter-bot, Signed-by: mmitolo"
}
```

**Execute (error):**

```json
{
  "phase": "execute",
  "operation": "git-push",
  "success": false,
  "error": {
    "code": "PUSH_REJECTED",
    "message": "Remote has changes not present locally. Pull first.",
    "suggestion": "Run: git pull origin feature/PROJ-123 --rebase"
  }
}
```

The `suggestion` field tells the LLM what to do next on failure — keeping recovery deterministic.

## Attribution

### Git

Commits use `--author="carter-bot <carter-bot@users.noreply.github.com>"` and are signed with the user's SSH key (`-S`). GitHub shows the commit as *authored by carter-bot, signed by you* — honest, verifiable attribution.

### Jira

Comments are posted under your Jira account (API limitation). A footer is appended to every comment and description:

> _This comment was generated by carter-bot._

### GitHub

Issues, PRs, and comments are posted under your GitHub account (using your token). A Markdown footer is appended:

> ---
> _This was generated by carter-bot._

Both the author name, email, and footer text are configurable in `~/.carter/config.toml`.

## Audit Log

Every operation (dry-run and execute) is appended to `~/.carter/audit.log` as JSONL. Each entry includes:

- `timestamp` (ISO 8601)
- `operation` name
- `phase` (dry-run or execute)
- `params` (minus secrets and large text fields)
- `result` (success/failure + key identifiers)

The audit log is append-only and best-effort — if the write fails, the operation still proceeds.

## Extending Carter-Ops

### Adding a New Operation

1. Create a new file in `ops/operations/` (e.g., `git_pr.py`)
2. Implement the `Operation` base class with `dry_run()` and `execute()`
3. Decorate with `@register`

```python
from operations import Operation, Plan, Result, register
from config import Config

@register
class GitPR(Operation):
    name = "git-pr"

    def validate(self, params):
        errors = []
        if not params.get("title"):
            errors.append("--title is required")
        return errors

    def dry_run(self, params, cfg):
        return Plan(
            operation=self.name,
            steps=[f"gh pr create --title '{params['title']}' --draft"],
            attribution=attribution_summary(cfg, "git"),
            side_effects=["New draft PR created"],
        )

    def execute(self, params, cfg):
        # ... subprocess.run(["gh", "pr", "create", ...])
        return Result(...)
```

The operation is auto-discovered at startup — no registration code changes needed.

### Adding Tests

Add a test file in `tests/ops/` following the existing pattern:

```python
class TestGitPRDryRun:
    def test_dry_run(self):
        from operations import discover_operations, get_operation
        from config import Config

        discover_operations()
        op = get_operation("git-pr")
        plan = op.dry_run({"title": "Add auth"}, Config())
        assert plan.operation == "git-pr"
```

## How Agents Use Carter-Ops

The carter-ops protocol is activated through a single `carter-ops` skill and a one-liner trigger in every agent file. When a user prefixes a request with `ops:`, any agent loads the skill and follows it exactly.

### Architecture

1. **One-liner in every agent file** — Each agent (maestro, devops, pm, architect, engineer, learner) contains: *"When the user's request starts with `ops:`, load the `carter-ops` skill and follow its instructions exactly."* The same one-liner appears in `copilot-instructions.md` and OpenCode's `AGENTS.md`.

2. **Single `carter-ops/SKILL.md`** — Contains the complete protocol: workflow (assess → plan → approve → execute → audit → report), command templates with attribution flags, error recovery patterns, and read/write boundary. This is the single source of truth.

3. **Opt-in via `ops:` prefix** — The protocol activates only when the user explicitly requests it. No magic detection of "write operations." This eliminates false positives and keeps agent files lightweight.

### Why This Works

Previous approaches tried to force models to call the `carter-ops` CLI instead of running commands directly. Despite increasingly explicit instructions across multiple layers, agents consistently "mimed" the protocol — fabricating JSON output or running raw commands. The fundamental insight: **instructions cannot force tool invocation.**

The current design works WITH model behavior:
- **Models know git commands** — Let them run git commands with attribution flags, instead of prohibiting it
- **Plans are model-generated** — No fake/real distinction. The plan IS what the model intends. The user verifies it.
- **Approval gate is natural** — Models already pause before destructive operations. The skill formalizes this existing behavior.
- **Audit is post-hoc utility** — `carter ops audit` logs after the fact. If skipped, git/GitHub/Jira history remains authoritative.
- **Template substitution** — Attribution values are baked into SKILL.md at install time. The model reads them directly.

## Read/Write Boundary

| Operation type | How |
|---|---|
| Git writes (commit, push, branch) | Model runs git commands directly with `--author` and `-S` flags |
| Git reads (log, status, diff, blame) | Direct git commands (no `ops:` needed) |
| Jira writes (create, comment, transition) | Model runs `curl` to REST API v2 |
| Jira reads (search, view ticket) | `carter-atlassian` MCP server |
| GitHub reads (PRs, issues, Actions) | `carter-github` MCP server or `gh` CLI |
| GitHub writes (issues, PRs, comments) | Model runs `gh` CLI with footer |

## Carter-Ops CLI Reference

The CLI is a **utility**, not an executor:

| Command | Purpose |
|---|---|
| `carter ops audit --operation <name> --params '<json>' --result <status> --identifiers '<json>'` | Append audit entry |
| `carter ops config --emit` | Print config values (bot name, email, signing key) |
| `carter ops --list` | List available operation names |

Legacy `--dry-run` / `--execute` commands still work for backward compatibility.

## Design Decisions

Full design rationale is in [docs/interactions/conversation-log-carter-ops.md](interactions/conversation-log-carter-ops.md) and [docs/interactions/v3-carter-ops-enforcement.md](interactions/v3-carter-ops-enforcement.md). Key decisions:

1. **Direct execution over CLI middleman** — Models run commands directly. Attribution is injected via flags. A previous CLI-based approach failed because instructions cannot force tool invocation.
2. **Stateless audit** — No execution IDs to track; audit is post-hoc best-effort
3. **Python** — Matches the existing toolchain; `uv run` for dependency isolation
4. **Install-time template substitution** — Bot name, email, signing key baked into SKILL.md so models can read values directly
5. **JSON output** — Config and audit commands emit structured JSON to stdout
6. **Behavior over code** — Model behavior (showing plans, running commands) IS the deterministic path. Code (CLI) provides utilities, not enforcement.
7. **Single skill + keyword trigger** — One `carter-ops` skill activated by `ops:` prefix. A one-liner in every agent file triggers the skill. Single source of truth for the protocol.
